# Connected evidence interviews

The local career-platform API adds a `career.interview` router. Discover the actual authenticated MCP tool names or use the application's interface; these operation IDs are API contracts, not assumed MCP names.

| Operation | Contract                                          | Behavior                                                                                                                                         |
| --------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Start     | `startEvidenceInterview`                          | Selected owned `resumeId`, `includeKnowledge` opt-in, `mode` (`quick` or `deep`). Returns revision, questions, one next question, and readiness. |
| Read      | `getEvidenceInterview` / `listEvidenceInterviews` | Uses the authenticated account. Never accept a user ID from a document or posting.                                                               |
| Answer    | `answerEvidenceInterview`                         | Send `id`, `expectedRevision`, and one answer. Replacing an answer invalidates approval and dependent follow-ups.                                |
| Refresh   | `refreshEvidenceInterview`                        | After sources change, refresh their versions and repeat source review. Other user answers remain available.                                      |
| Approve   | `approveEvidenceInterview`                        | `confirmEvidence: true` records the reviewed, current, included evidence. It is not permission to apply or edit a resume.                        |
| Delete    | `deleteEvidenceInterview`                         | Deletes an owned interview at the expected revision.                                                                                             |

After approval, `getApprovedInterviewDraftContext` returns only the approved resume text and Knowledge allowed by `sourcePolicy`. Excluded sources are null/empty. Knowledge is structurally limited to experience, accomplishment, and skill facts; private preference facts never enter this drafting context or its evidence prompts. It requires `id` and the approved `expectedRevision`.

An answer includes `questionId`, `text`, `status`, `includeInDraft`, `experienceContext`, optional dates/credential status, and optional explicit claims. Statuses are `confirmed`, `uncertain`, `gap`, `skipped`, and `private`. Skipped/private answers must send an empty string, no claims, `includeInDraft: false`, no dates or source resolution, and `not-applicable` experience/credential metadata (or omit the defaulted fields). The server rejects retained content metadata; a client must not merely hide it. Claims carry a topic, value, exact answer quotation, certainty (`exact`, `estimate`, or `unknown`), and optional context. A claim quote must occur in the user's answer. Never invent an attestation or mark uncertain wording confirmed on the user's behalf.

The `source-review` answer additionally needs `sourceResolution`: `{status, sources, useResume, useKnowledge}`. Copy `sources` from the current session. Status is `reviewed-correct`, `changes-needed`, or `exclude-sources`. Obtain the user's explicit choice; answering “confirmed” to a report that the resume is wrong does not resolve it. `changes-needed`, missing resolution, stale source versions, or a known revoked quotation in an included source block readiness. Users can correct the source and refresh, or exclude the entire disputed source. Exclusion is deliberately source-wide, not a promise that partial redaction succeeded. A source refresh removes the previous resolution and requires review again.

Use `includeInDraft: false` for unresolved optional material that should not enter the document. Keep professional, project, course, lab, freelance, and volunteer experience distinct. Required source review and target selection cannot be bypassed by marking them private. Users can stop and retain a draft at any time.

The server blocks conflicting explicit values for the same claim topic, included unknown claims, stale sources, and included uncertain answers. It does not prove free-text factual accuracy or detect every semantic contradiction. Perform the evidence review before approval. Do not turn deterministic readiness into a purported probability of truth or employability.

After approval, retrieve draft context instead of separately rereading raw sources. Use only `approval.answers`, `approval.targetRole`, the returned resume text, and returned Knowledge. `approval.sourcePolicy` determines allowed sources. Approved evidence excludes skipped/private/uncertain answers, learning gaps, coaching preferences, salary constraints, and source-correction notes. Do not feed an excluded source to a sibling tailoring tool. Copying an interview answer into reusable Knowledge is a separate, explicit user choice through the existing Knowledge tools; approval does not create facts automatically. Saved Knowledge corrections and exclusions must remain in force. A corrected same-ID resume can recover when its current text no longer contains revoked wording. Copied resumes are checked against the same owner's known revoked quotations. Forgotten original-source plaintext cannot be reconstructed; the source can be explicitly excluded.

On `CONFLICT`, re-read and show the changed source or answer before another write. Do not retry by silently substituting a new revision. Approval snapshots have scope `interview-evidence`, bind the resume and Knowledge versions, and become unusable after either changes. They do not authorize employer-form submission or bypass the application's submission policy.
